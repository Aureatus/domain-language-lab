# Project instructions

## Intent

This is an unnamed language research/design repository with user-authorized implementation of one small example application to test the architecture. Keep implementation scoped to that experimental vertical slice. Preserve the user's priorities: Ash-like derivation; policy-derived approvals; implicit action/change events with optional business facts; grouped updates; relationship-driven one-way/bidirectional propagation; sophisticated T3 Code-like applications; user-defined renderers and verification/output adapters; scoped interop; and tests of our mappings rather than copies of upstream suites.

Do not name the language Lumen. Do not center it on Lucent-specific proposal terminology. Use general resources/actions/policies and multiple example domains.

## Research discipline

- Read README.md and the relevant local memo before researching further.
- Use primary sources, selected implementation and in-progress work where relevant. Record exact versions/commits for implementation claims when possible.
- State read depth: overview, selected sections, source inspection, independent execution or proof audit. Never claim full-book reading from an abstract.
- Label facts, hypotheses, design proposals and open questions. Keep failed/unverified sources out of evidence chains.
- Every strong guarantee names its scope, assumptions, trusted components and uncovered boundaries.
- Keep the source law separate from implementation/proof scripts. Surface weakened laws as semantic changes.
- No silent fallback from unsupported proof/model constructs to a passing result.
- Distinguish deterministic derivation from deterministic external execution. Clock, randomness, scheduling, I/O and external outcomes need explicit inputs/contracts.

## Artifacts

Prefer stable semantic IDs, versioned contracts, source maps, and evidence-linked traces. Generated docs, diagrams and videos are projections, not independent authorities. A storyboard's sequence must not invent causal order. Example fixtures are labeled illustrative until executed against a specified model.

Keep library-owned behavior separate from integration obligations. No application implementation, dependency installation or remote publication unless the task calls for it.

## Specialist use

The user has requested specialist agents. Delegate bounded research or review when it improves the task; not every change requires delegation. Assign disjoint files. Children do not delegate. Consolidate findings and resolve conflicts in the primary session. Agent definitions inherit the current model; do not pin or silently change providers/models.

Research agents should return: key finding, evidence/read-depth, proposed decision, limitation, open question, and changed paths. The evidence reviewer is read-only.
